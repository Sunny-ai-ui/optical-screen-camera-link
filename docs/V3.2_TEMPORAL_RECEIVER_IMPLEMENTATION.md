# V3.2 Temporal Receiver Implementation

## Goal

V3.2 changes the receiver from a single-camera-frame decoder into a temporal evidence decoder. A camera frame is treated as one observation of an optical sender frame. Multiple compatible observations may be fused before Reed-Solomon recovery.

## Safety and compatibility

- Existing V3 G32/G48/G64 profiles are unchanged.
- Existing RS(15,11), spatial interleaving and protocol CRC remain authoritative.
- Temporal mode is the default receiver path.
- Append `?mode=legacy` to `apps/receiver-v3/` to use the previous single-frame path.
- Different V3 profiles are never fused.
- Low-agreement observations start a new temporal group instead of being mixed.
- Protocol CRC remains the final per-packet integrity gate.

## Runtime pipeline

```text
camera
  -> locator acquisition/tracking
  -> coarse V3/profile detection
  -> native-resolution rectification
  -> decoder worker observation
  -> quality gate
  -> temporal observation group
  -> independent shape and colour weighted fusion
  -> confidence/erasure stream
  -> RS(15,11)
  -> packet CRC/protocol decode
  -> transfer reassembly
```

## New modules

### `apps/receiver-v3/temporal-fusion.js`

Provides:

- weighted shape voting
- weighted colour voting
- fused confidence generation
- observation agreement scoring
- transition-safe `TemporalObservationStore`

Shape and colour are fused separately so a colour error in one camera sample does not automatically destroy an otherwise stable shape decision, and vice versa.

### `apps/receiver-v3/frame-quality.js`

Produces a bounded quality score from timing separation, signature separation, camera pixels per cell and decoder confidence. Weak observations are rejected before RS attempts.

### `apps/receiver-v3/v3-decoder-worker.js`

Runs expensive V3 cell observation work outside the main browser thread when Web Workers are available. The main thread falls back to local observation if Worker support is unavailable.

### `apps/receiver-v3/v3-decoder.js`

The decoder is now split into two stages:

- `observeV3ImageData()` / `observeV3Roi()` — optical evidence only
- `decodeV3Observation()` — Reed-Solomon packet recovery

`decodeV3Roi()` remains as the legacy combined wrapper.

## Temporal grouping

The receiver uses early Reed-Solomon codeword symbols as an optical identity region for transition detection. The identity comparison intentionally focuses on the beginning of the protected envelope, which contains the packet/protocol header and early payload rather than comparing the entire padded optical frame.

A group is reset when:

- the profile changes;
- the observation window expires;
- identity agreement falls below the transition threshold.

This prevents obvious sender-frame transitions from being fused together while retaining backward compatibility with the existing optical frame layout.

## Progressive recovery

A high-quality single observation may be attempted immediately. Otherwise the receiver normally collects at least two observations. If RS is uncorrectable, the group is retained and later camera evidence is fused into a new RS attempt.

This changes failure semantics from:

```text
RS fail -> discard camera frame
```

to:

```text
RS fail -> keep optical evidence -> collect another compatible observation -> retry
```

## Metrics added

The receiver now exposes:

- receiver mode
- observation-group size
- frame quality
- cell agreement
- temporal attempts
- temporal successes
- detected frame transitions
- worker skips while classification is busy
- decoder latency

Existing timing, shape confidence, colour confidence, RS correction and protocol metrics remain.

## Test coverage

The temporal test suite covers:

- low-confidence conflicting observations;
- independent shape/colour fusion;
- transition disagreement;
- profile isolation;
- group reset on low agreement;
- a synthetic case where temporally fused evidence recovers the original packet despite degraded individual observations;
- frame-quality gating.

## Remaining experimental work

The code intentionally does not change the wire protocol or introduce fountain coding yet. Those are transport-layer changes and should be evaluated after real camera recordings confirm the receiver-layer improvement. An explicit optical frame-ID/header remains preferable long term; the current release uses protected-envelope identity agreement to preserve compatibility with existing V3 senders.

## Physical validation procedure

1. Start with V3 Robust G32 at 1 fps.
2. Open the V3 receiver in default temporal mode.
3. Keep at least 10 camera pixels per logical cell where possible.
4. Record observation-group size, cell agreement, RS rejects and successful packets.
5. Repeat the same setup with `?mode=legacy`.
6. Compare successful packets and RS rejects under identical geometry.
7. Only after G32 is repeatable move to G48 and then G64.

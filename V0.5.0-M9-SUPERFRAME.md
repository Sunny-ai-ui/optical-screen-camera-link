# v0.5.0 M9 3×3 Optical Superframe

M9 is an experimental parallel screen-to-camera format built alongside the proven G32 production path.

## Goal

Improve stability, repeatability and runtime efficiency by replacing one monolithic optical payload area with nine smaller independently recoverable tiles, while keeping the link strictly one-way.

## Layout

- One shared outer locator frame and one 768×768 rectified logical ROI.
- 3×3 fixed mini-tiles.
- Each tile is 13×13 cells.
- One-cell timing border per tile.
- Top-border self-calibration for four colours and four shapes.
- One centre tile marker.
- 120 protected data symbols per tile.

## Tile protection

Each tile carries a 44-byte envelope:

- 2 bytes: visual frame ID
- 40 bytes: shard data
- 2 bytes: CRC16-CCITT

The 44-byte envelope becomes 88 nibbles and is encoded as exactly eight RS(15,11) codewords, producing 120 optical symbols.

## Spatial parity

Tiles 0–7 carry eight 40-byte data shards.

Tile 8 carries the XOR of all eight data shards.

This allows the receiver to reconstruct one missing data tile when the parity tile and the other seven data tiles are valid.

Total protected packet capacity per displayed superframe: 320 bytes.

## Global header

A repeated 40-bit black/white header carries:

- M9 magic
- format version
- 16-bit visual frame ID
- 9-bit packet length
- CRC8

The repeated header also provides robust orientation detection before tile decoding.

## Receiver runtime

The M9 receiver is intentionally lightweight:

1. Detect/track the same four outer locators already used by G32.
2. Rectify the full screen once.
3. Read the repeated M9 header.
4. Crop only the nine known tile locations.
5. Cache any tile that passes RS + CRC16.
6. On later camera observations of the same visual frame, decode only missing tiles.
7. Recover one missing data tile from spatial parity when possible.
8. Reassemble the original existing fountain packet.
9. Feed that packet into the existing fountain and payload integrity stack.

No nine-way finder search is required.

## Compatibility and rollout

- G32 remains the production fallback.
- M9 has separate sender and receiver pages.
- Existing protocol packets, fountain transport, payload compression and SHA-256 verification remain unchanged.
- No reverse communication channel is introduced.
- G48/G64 remain outside the production path.

## Initial physical settings

Start with:

- 2.0 s dwell per M9 superframe
- fullscreen sender
- 100% fountain overhead
- same camera distance that gives roughly 14–18 px/cell on G32

M9 mini-tile cells are physically smaller than G32 cells, so the first test should prioritize tile success rate and decoder latency before reducing dwell.
